# 맞춤 추천 — 대화 기반 조건 수집 및 후보 선별 v0.9

## 기존 문제 (v0.8)

- 사용자가 `추천해줘`라고만 말해도 예산 100만원, 개발 수준 `BASIC`, 위험 성향 `MEDIUM`, 월 비용 3만원 상한을 코드가 임의로 적용했다.
- `objectives`는 추천 요청에 포함되지만 규칙 기반 점수 산정에 반영되지 않았다.
- 선호 기술이 맞지 않는 매물도 점수를 낮춰 포함했다. 적합한 후보 수 제한이 없어 전체 매물이 추천처럼 표시될 수 있었다.

## v0.9에서 변경한 흐름

1. 사용자 요청이 맞춤 추천에 해당하면, 채팅 맥락에서 **구매 목적, 예산 상한, 개발 수준, 위험 허용도**가 명시되었는지 확인한다.
2. 부족한 정보는 대화에서 **한 번에 한 가지 질문**으로 수집한다. 하나의 문장에 모든 정보를 알려주면 추가 질문 없이 진행한다.
3. 모르는 수준이나 위험 성향에 한해 사용자가 `모름` 또는 `기본값으로`를 **명시적으로 선택한 경우에만** 기본 가정을 쓰고 응답에 표시한다.
4. 사용자가 직접 요청한 기술과 유형을 필수 조건으로 반영할 수 있으며, 예산·명시한 월 운영비 상한도 필터로 적용한다.
5. 구매 목적별 점수 규칙을 반영하고, **적격 후보 수와 상위 최대 3건**을 분리해 보여준다. 매물이 없으면 억지로 추천하지 않는다.
6. AI 모드와 규칙형 모드 모두 추천 전에 **동일한 조건 수집 및 검증 로직**을 사용한다. 다른 도구 호출은 그대로 유지된다.

## 사용자 대화 예시

- `맞춤 추천해줘` → 구매 목적 질문 → 예산 질문 → 개발 수준 질문 → 위험 허용 질문 → 추천
- `100만원 이하 Python 웹서비스 추천해줘. 개발 학습이 목적이고 초급, 저위험` → 추가 질문 없이 기술·유형·예산 필터 실행
- `내 프로필로 추천해줘` → 현재 방문자가 개인 위임 토큰을 연결한 경우 `buyer_profile:read`를 사용해 **본인 저장 프로필만** 조회. 누락 조건만 질문. 토큰 없거나 권한 없으면 조회 불가를 명시하고 대화 입력을 안내
- `취소` → 진행 중인 추천 문답을 취소

## 실제 점수와 한계

- 예산, 상태, 명시한 기술/유형 요구 및 월 운영비 상한은 확실히 확인 가능한 데이터의 하드 필터다.
- 기술 숙련도와 운영 가능성, 실사 점수는 **규칙 기반의 추정**이다. 매출, 권리 이전, 실제 구동은 별도 검증 필요.
- 수익 창출 목적에서는 **검증된 수익**과 **판매자의 수익 주장**을 혼동하지 않는다. 검증 자료가 없는 후보는 위험 항목에 표시한다.
- 목적은 현재 `학습/포트폴리오/수익/운영/재판매` 등 대표 패턴을 중심으로 점수에 반영된다. 자유로운 업종, 기능 요구를 완전한 의미 분석으로 해석하지는 못하므로 추후 OpenAI 추출 기능과 데이터 스키마 확장이 필요하다.
- 상위 3건 제한은 선택 지원을 위한 표시 정책이다. 해당 조건을 만족하는 매물이 3건 이하면 모두 표시될 수도 있다.
- 새 대화를 열면 이전 대화의 추천 조건은 보존되지 않는다. 저장 프로필 기능은 사용자별 ProjectAgain 계정/위임 권한이 필요하다.

## 보안·연동 제약

- Live 모드에서 공개 매물 검색, 로컬 평가와 작업 기록은 유지하고, 플랫폼에 대한 **실제 변경 요청은 계속 차단**한다.
- 개인 구매 조건 조회는 사용자 자신의 단기 Bearer 위임 토큰이 있는 경우에만 가능하다. 공용 Streamlit Cloud Secrets의 키를 모든 방문자에게 적용하지 않는다.
- 새로운 유료 OpenAI 호출을 조건 수집 단계에 추가하지 않았고, API 키/토큰 원문은 응답이나 로그에 포함하지 않는다.
- 실제 ProjectAgain v0.13 HTTPS 서버와 Streamlit Cloud, OpenAI API 통신은 이 버전 제작 환경에서 별도로 검증하지 못했다.
